Chapter 1 – Project Vision & Business Overview
1.1 Document Purpose
This document defines the technical and business foundation for the Delix Cargo Delivery Platform.
It is the primary implementation guide for developers and AI-assisted tools such as Cursor.
Every feature, API, user interface, workflow, database design, and system interaction must follow the requirements in this document.
This project is intended for production deployment, not as a prototype or demonstration.

1.3 Business Vision
Delix provides a modern digital platform that connects customers needing cargo transportation with verified drivers who own cargo vehicles.
Unlike passenger ride-hailing applications, Delix focuses entirely on moving goods.
The application enables customers to request transportation for items ranging from small documents to large construction materials using the most appropriate vehicle.
The system automatically finds the nearest available driver with the required vehicle type, calculates the estimated route, estimated arrival time, and delivery cost, and provides real-time tracking from pickup to delivery.

Drivers can only accept bookings matching their registered vehicle category.

Administrators can override bookings only through authorized workflows.
Commission rules are enforced after the configured trip threshold.
All financial transactions must be logged.

DELIX CORE GUIDE
Chapter 6 – Performance, Scalability & Development Standards
6.1 Purpose
This chapter defines the technical standards required to build a fast, scalable, secure, and maintainable Delix platform.
Every developer and Cursor AI implementation must follow these standards.
The objective is to ensure the application performs reliably on low-end and high-end devices while supporting future growth.
6.2 Performance Goals
The platform should feel responsive from the first interaction.
Target performance goals:
Application cold start: less than 3 seconds
Screen transition: less than 300 milliseconds
API response (average): less than 500 milliseconds
Map interaction: smooth at 60 FPS
Vehicle list rendering: less than 200 milliseconds
Booking creation: less than 2 seconds
Live location updates: every 3–5 seconds (configurable)
Performance must remain stable even when many users are active.
6.3 Mobile Performance Standards
The User App and Driver App must:
Avoid unnecessary component re-renders.
Use memoized components where beneficial.
Load only required data.
Lazy load heavy screens.
Cache images.
Reuse UI components.
Minimize bundle size.
Avoid blocking the main thread.
Never fetch data that is not immediately needed.
6.4 State Management Standards
Use Zustand for global state.
Create separate stores for each feature.
Recommended stores:
authStore
bookingStore
locationStore
driverStore
vehicleStore
paymentStore
notificationStore
socketStore
settingsStore
profileStore
Guidelines:
Keep stores focused on one responsibility.
Avoid storing derived data if it can be computed.
Reset temporary state after booking completion.
Persist only data that should survive app restarts (for example, authentication and language).
6.5 API Standards
All API requests should pass through a shared API service.
Requirements:
One Axios instance.
Request interceptor.
Response interceptor.
Automatic JWT attachment.
Automatic token refresh.
Standardized error handling.
Timeout configuration.
Retry temporary failures when appropriate.
Do not call APIs directly from UI components.
6.6 Caching Strategy
Use caching to reduce unnecessary network requests.
Recommended caching:
User profile
Vehicle categories
Pricing configuration
Supported cargo categories
Static application settings
Do not cache:
Driver locations
Live booking status
Payment confirmations
These must always use fresh data.
6.7 Image Optimization
All uploaded images should be optimized before display.
Guidelines:
Compress images where appropriate.
Cache downloaded images.
Display placeholders while loading.
Use responsive image sizes.
Remove unused metadata before upload if supported.
Image types include:
Profile photos
Vehicle photos
Cargo photos
Driver documents
6.8 Map Performance
The map is the most resource-intensive component.
Optimize by:
Rendering only visible markers.
Clustering markers if necessary in future versions.
Updating only changed driver positions.
Limiting unnecessary camera movements.
Avoiding repeated route calculations.
Reusing map layers and icons.
6.9 Socket.IO Standards
Socket connections should:
Connect only after authentication.
Automatically reconnect after temporary network loss.
Handle duplicate events safely.
Disconnect cleanly during logout.
Recommended events:
booking_created
booking_accepted
driver_location_updated
driver_arrived
trip_started
trip_completed
notification_received
6.10 Database Performance Standards
The database must be optimized for both read and write operations.
Requirements:
Use UUID primary keys.
Create indexes on frequently queried columns.
Normalize data.
Avoid duplicate records.
Use transactions for critical operations.
Optimize joins.
Support pagination.
Frequently queried fields should be indexed, such as:
Phone number
Booking status
Driver status
Vehicle category
Created date
Geographic location (using PostGIS)
6.11 Backend Performance Standards
The backend should:
Validate all requests.
Return only required fields.
Avoid unnecessary database queries.
Use asynchronous processing where appropriate.
Log errors without exposing sensitive information.
Keep controllers thin and business logic inside services.
6.12 Security Standards
Authentication:
Phone number + OTP only.
JWT access tokens.
Refresh tokens.
Communication:
HTTPS for all requests.
Secure WebSocket connections.
Data:
Validate all input.
Sanitize uploaded files.
Enforce authorization checks.
Never expose internal server errors to clients.
Administrative actions should be logged for auditing.
6.13 Coding Standards
General rules:
Use TypeScript in strict mode.
Follow consistent naming conventions.
Write reusable components.
Keep functions small and focused.
Avoid duplicated logic.
Separate UI, business logic, and data access.
Document complex logic.
Folder names, file names, and component names should remain consistent throughout the project.
6.14 Git Workflow
Recommended branch structure:
main
develop
feature/*
bugfix/*
hotfix/*
release/*
Every feature should be developed in its own branch and merged through code review.
6.15 Testing Strategy
Testing should include:
Unit tests for business logic.
Integration tests for APIs.
End-to-end testing for critical booking flows.
Manual testing on multiple Android devices.
Network interruption scenarios.
GPS disabled scenarios.
Payment failure scenarios.
6.16 Monitoring & Logging
The platform should log:
API errors
Authentication failures
Booking failures
Payment failures
Driver matching errors
Socket connection issues
Logs should support troubleshooting without exposing user-sensitive information.
6.17 Production Readiness Checklist
Before release, verify:
All screens are responsive.
No hardcoded strings.
Localization works.
Authentication is secure.
Booking flow completes successfully.
Driver tracking functions correctly.
Payment methods are operational.
Error handling is complete.
Performance targets are met.
Database queries are optimized.
Accessibility requirements are satisfied.

Before writing code, Cursor must:

Reuse existing components, hooks, and services.
Avoid recreating working functionality.
Follow this Core Guide as the source of truth.

DELIX CORE GUIDE
Chapter 7 – Global Business Rules & System Standards
7.1 Purpose
This chapter defines the business rules that apply across the entire Delix platform.
Every application (User App, Driver App, Backend, Database, and Admin Panel) must follow these rules.
Business rules must be enforced by the backend. The mobile applications should provide a clear user experience, but the backend is the final authority for validation and decision-making.
7.2 User Rules
A customer must:
Register using a valid phone number.
Verify the phone number with OTP before accessing the platform.
Maintain one active account per phone number.
Provide accurate pickup and destination locations.
Select the correct cargo category.
Choose an appropriate vehicle type.
Accept the displayed estimated price before confirming a booking.
A user cannot:
Create multiple active accounts with the same phone number.
Create a booking without OTP verification.
Modify a booking after the driver has started the trip.
Submit incomplete booking information.
7.3 Driver Rules
A driver must:
Complete registration.
Upload all required documents.
Wait for administrator approval.
Register at least one vehicle.
Keep vehicle information accurate.
Enable location services while online.
A driver cannot:
Receive bookings before approval.
Receive bookings while offline.
Accept bookings for vehicle categories that do not match their registered vehicle.
Accept multiple active deliveries at the same time unless future multi-order support is introduced.
7.4 Vehicle Rules
Supported vehicle categories:
Lada
Pickup Truck
Mini Truck
Large Truck

Economy

Industrial

Estimated arrival multiplier

7.5 Booking Rules
A booking must include:
Pickup location
Destination
Vehicle category
Vehicle model
Cargo category
Payment method
Optional fields:
Cargo description
Cargo images
Loading assistance
Unloading assistance
Special instructions
A booking receives a unique booking reference generated by the backend.
7.6 Pricing Rules
The final booking price is calculated by the backend.
Pricing factors include:
Base vehicle price
Distance
Vehicle model
Cargo category
Loading service
Unloading service
Dynamic pricing (future)
Promotional discounts (future)
The User App should display an estimated price before booking confirmation.
The backend calculates the final payable amount.
7.7 Driver Matching Rules
When a booking is created:
Search drivers within the configured search radius.
Filter by vehicle category.
Filter by approval status.
Filter by online status.
Filter by availability.
Sort by shortest estimated arrival time.
Send the booking request.
Wait for a response.
If rejected or timed out, continue with the next driver.
Continue until a driver accepts or the search limit is reached.

7.9 Payment Rules
Supported payment methods:
Telebirr
Commercial Bank of Ethiopia (CBE)
Cash
Business rules:
Payment method is selected before booking confirmation.
Online payments require backend verification.
Cash payments are marked as pending until delivery completion.
Every payment creates a transaction record.
7.10 Commission Rules
Drivers operate on a commission cycle.
Initial business rule:
Driver completes 10 successful deliveries.
The app temporarily pauses new booking assignments.
Driver is prompted to pay the required commission through Telebirr.
After successful payment verification, booking assignments resume.
The commission cycle value should be configurable from the Admin Panel.
7.11 Location Rules
The application must:
Request location permission during onboarding.
Allow manual location selection.
Detect the user's current location when permission is granted.
Support GPS updates during active deliveries.
Preserve selected pickup and destination until the booking is completed or canceled.
